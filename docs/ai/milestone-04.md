## Evidence preparation and index

Hard ceilings: 12 files, 12 KiB per file, 64 KiB total normalized content; optional
limits can tighten these values only. Prompt size including instructions/schema is
capped at 128 KiB. Raw model response is capped at 64 KiB before parsing.
Files exceeding a budget are skipped whole, not silently truncated.
Priority: source, nonsecret configuration, manifests, tests, documentation; ties
sort by evidence ID and canonical path. File filtering reuses M2 path/content gates,
then rejects known instruction-injection markers, email addresses and literal
analysis/user identifiers in file metadata/content. These are conservative heuristics.
No CV or userId is included in the prompt. Code is never executed.

Each index entry contains `evidenceId`, `fileRef`, `filePath`, `content`,
`sourceType`, `origin`, optional `revision`, and `kind`. Original evidence identity
and repository origin/revision are preserved. GitHub origins must be canonical.
`fileRef` is `file_` plus the first 24 hexadecimal SHA-256 characters of the
JSON tuple [evidenceId, path, revision, normalized content]. CRLF and CR become LF;
no whitespace or other content normalization is performed. Matching later uses
exact substring of this same content. Duplicate evidence IDs are rejected by M3.

Coverage records sourceCount, includedSources, discoveredFiles, availableFiles,
sentFiles, skippedFiles and sentContentBytes. SkippedFiles = discoveredFiles -
sentFiles, including reader omissions. Warnings are fixed enums without raw content.
Source partial status and budget omissions propagate to result `partial`; completed
means processing of the available safe input completed, not validated competence.

## Prompt, output and validation

Prompt version: `buktiva-skill-extraction-1.0.0`.
Trusted system instructions/rubrics are separate from JSON-encoded project data,
explicitly labelled untrusted. Instructions prohibit invented IDs/files, authorship
assumptions, dependency-as-mastery claims, readiness scores and roadmap generation.
The Google JSON response schema constrains IDs and references to supplied values.
Local validation remains mandatory because structured output alone is insufficient.

Gemini returns `{ "skills": [...] }`. Each item has official `skillId`,
`evidenceStatus` (`observed_technology`, `implementation_evidence`,
`insufficient_evidence`), `evidenceRefs` and a nonblank `reason`.
Each reference has evidenceId, fileRef, filePath and quote (up to 400 characters).
The application wraps this in analysisId, status, model, promptVersion,
datasetVersion, coverage, warnings and optional safe error metadata.
No confidence/readiness fields are accepted.

Validation rejects the entire model output if any item is invalid. Strict Zod rejects
extra properties, invalid enums/types and empty output. Every official skill must
occur exactly once; unknown, duplicate or omitted IDs fail. References must match
the index, original input evidence, file identity and exact normalized substring.
Repeated references fail. Insufficient evidence must have no references. Other
statuses require references; implementation additionally requires source/test evidence.
Manifest/config/documentation alone supports observed technology only. Reasons are
checked for known secret/PII/injection markers and score/gap/roadmap language.
Skills and references are sorted deterministically.

Synthetic example (excerpt, not a live Gemini result): the fixture's
`src/identity.ts` contains `export function identity<T>(value: T): T { return value; }`.
The test mock returns the input TypeScript skill ID, implementation_evidence,
the actual generated reference and that exact quote; the validator accepts it.
Changing the skill ID, evidence ID, fileRef/path or quote in otherwise valid JSON
causes rejection. Mock output exists only in tests and is never a production fallback.

## Provider, retries and manual live diagnostic

The adapter calls the installed official SDK only through M1 `gemini.ts`, using
application/json, responseJsonSchema, systemInstruction and maxOutputTokens=8192.
It retries only 503/504, with 250 ms exponential backoff: default two attempts;
configurable maximum three attempts (250/500 ms delays). 429, permanent errors,
empty or oversized responses are not retried. Each attempt has M1's 30-second
timeout; default upper request budget is approximately 60.25 seconds, excluding
local processing. No automatic model fallback is enabled in the service.

Run offline checks from the workspace (PowerShell uses npm.cmd/npx.cmd):

```powershell
npm.cmd run test:ai
npm.cmd run test:ingestion
npm.cmd run test:analysis
node --test scripts/test-gemini-server.mjs
npm.cmd run lint
npx.cmd tsc --noEmit
npm.cmd run build
npm.cmd audit --omit=dev
```

Manual live opt-in, only after reviewing the synthetic fixture and API tier:

```powershell
$env:BUKTIVA_RUN_LIVE_GEMINI_TEST = '1'
npm.cmd run test:ai:live
Remove-Item Env:BUKTIVA_RUN_LIVE_GEMINI_TEST
```

The command reads existing `.env.local` without printing it. It requires configured
key/model, imports provider/fixture only after opt-in and sends only synthetic data.
It logs model, status, duration and validation status/error codes, not raw request,
response or key. One request per model; at most two calls if a distinct
`BUKTIVA_LIVE_GEMINI_ALTERNATIVE_MODEL` was explicitly configured and the primary
failed 503/504. Alternative selection never changes production configuration.
Tests/build/install do not invoke live generation.

## Privacy, security and interpretation limits

Safety scanning is heuristic: unknown secrets, PII, obfuscated instructions and
semantically misleading code may evade detection. Public origins/paths can reveal
repository identity; permission and data handling review remain necessary before
real-user processing. Literal quote/provenance checks do not prove semantic skill
relevance, execution correctness, authorship or personal mastery. Model content must
remain an untrusted candidate for later validation. Skipped files can hide relevant
implementation; coverage is reported rather than claiming whole-repository review.

Google's terms distinguish unpaid and paid service data handling. Unpaid inputs and
outputs may be used to improve products and reviewed by humans; sensitive/confidential
data must not be submitted under those terms. Confirm the actual project tier,
applicable regional terms, user permission and retention policy before using real
data. No claim that configuring an API key establishes paid processing is made.
